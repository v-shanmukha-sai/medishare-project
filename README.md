# MediShare

Medicine donation and distribution platform built with PHP 8, Apache, PostgreSQL (Supabase), Bootstrap 5 and vanilla JavaScript. This version is ready for Render Docker deployment with Supabase Storage for permanent uploads.

## What changed for production

- Environment-first configuration (Render env vars), with `config/secrets.php` still supported for local XAMPP.
- Medicine images go to the public `medicine-images` bucket.
- Distributor and NGO documents go to private buckets and are shown to admins through short-lived signed URLs.
- Existing upload workflows, routes, UI, CSS and JavaScript are unchanged.
- Local development without a Supabase service key keeps saving to `uploads/` exactly as before.

No database schema changes and no MySQL dependencies.

## Local setup (XAMPP)

1. Import `database.sql` only on a **new** database. Do not run it against the existing production database.
2. Copy `config/secrets.example.php` to `config/secrets.php` and fill in the values.
3. Serve the project folder with Apache and open `index.html`.
4. Seed logins (password `admin123`): `admin@medshare.com`, `medplus@medshare.com`, `pharmalink@medshare.com`, `hope@medshare.com`, `citycare@medshare.com`.

`config/secrets.php`, `.env`, user uploads and logs are gitignored.

## Environment variables

Set these in Render (Environment tab) or in your shell for Docker. Environment values override `config/secrets.php`.

| Variable | Required | Purpose |
| --- | --- | --- |
| `APP_ENV` | yes (Render) | `production` disables the OTP file fallback. Defaults to production when `PORT` is set. |
| `DB_DSN` | yes* | PDO DSN, e.g. `pgsql:host=...;port=5432;dbname=postgres;sslmode=require` |
| `DATABASE_URL` | yes* | Alternative to `DB_DSN`; a `postgresql://...` URL |
| `DB_USER` | yes | Supabase pooler user (`postgres.PROJECT_REF`) |
| `DB_PASS` | yes | Supabase database password |
| `SUPABASE_URL` | yes | `https://PROJECT_REF.supabase.co` |
| `SUPABASE_ANON_KEY` | yes | Supabase Auth key for password-reset OTP |
| `SUPABASE_SERVICE_ROLE_KEY` | yes | Server-side Storage access. Never expose it to the browser. |
| `RAZORPAY_KEY_ID` | yes | Razorpay key id |
| `RAZORPAY_KEY_SECRET` | yes | Razorpay key secret |
| `RESET_SECRET` | yes | Long random string used to sign reset tokens |
| `MEDISHARE_EMAIL` | no | `true` enables notification email |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` / `SMTP_USER` / `SMTP_PASS` / `SMTP_FROM` | no | SMTP delivery for notification email (OTP email is sent by Supabase Auth) |

\* Provide either `DB_DSN` or `DATABASE_URL`.

`PORT` is supplied automatically by Render. Do not set it manually.

## Supabase Storage

The migration script creates these buckets:

| Bucket | Visibility | Contents |
| --- | --- | --- |
| `medicine-images` | public | medicine photos |
| `distributor-documents` | private | distributor license documents |
| `ngo-documents` | private | NGO registration documents |
| `invoices` | private | reserved for invoice files |
| `qr-codes` | private | reserved for QR code files |

Migrate the files already in `uploads/` **before** deploying:

```bash
php scripts/migrate-uploads.php
```

The script needs `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in the environment (or `config/secrets.php`). It uploads files, verifies each upload and never deletes the local originals. Database paths stay unchanged.

> Invoices in MediShare are generated by the browser print view (Dashboard → Orders → Invoice). There are no server-side invoice or QR image files in the current codebase; the private buckets are created for future use and the print flow is unchanged.

## Docker (local)

```bash
docker build -t medishare .
docker run --rm -p 8080:8080 --env-file .env -e PORT=8080 medishare
```

Open `http://localhost:8080`. The container reads `.env` through `--env-file`; `.env` is never copied into the image. For local testing without Supabase Storage, omit `SUPABASE_SERVICE_ROLE_KEY` and uploads fall back to the container filesystem (they will not survive a redeploy).

Health check: `GET /health.php` returns `{"ok":true}` when PostgreSQL is reachable.

## Render deployment

1. Push this repository to GitHub. `.env`, `config/secrets.php`, user uploads and logs are ignored.
2. In Render, choose **New → Web Service** and connect the GitHub repository.
3. Set **Runtime** to **Docker**. Render uses the `Dockerfile` in the repository root.
4. Choose the free plan and a region close to your Supabase project.
5. Add the environment variables from the table above. Use the Supabase **session pooler** host for `DB_DSN`/`DATABASE_URL`.
6. Set **Health Check Path** to `/health.php`.
7. Deploy. Render builds the image and routes traffic to the port in `$PORT`; Apache is started by `docker/entrypoint.sh` on that port.
8. After the first deploy, run the storage migration locally (step above). Re-uploaded files go to Supabase automatically.

Free-tier notes:

- Render spins the service down after inactivity; the first request after sleep is slow.
- The container filesystem is ephemeral. Uploaded files must use Supabase Storage, which is why the service role key is required in production.
- PHP sessions use the container filesystem, so a redeploy logs users out. Database data is unaffected.

## Password-reset email

The reset flow uses Supabase Auth OTP. Add `{{ .Token }}` to the Magic Link template under Supabase **Authentication → Email Templates**. Without `SUPABASE_ANON_KEY` the app uses a local OTP file in development only; in production it returns a configuration error instead of leaking OTPs.

## Apache / PHP

- Document root: `/var/www/html` (project root).
- PHP extensions: `pdo`, `pdo_pgsql`, `pgsql`, `curl`, `mbstring`, `fileinfo`, `openssl`, `opcache`.
- `mod_rewrite` enabled; existing `.htaccess` rules still apply.
- `config/`, `logs/`, `scripts/`, `docker/`, `.env`, SQL files and dotfiles are denied by Apache.
- Upload size limit: 2 MB per image (PHP limits set to 4 MB/8 MB).

## Composer

This project has no Composer dependencies, so no `composer install` step is required. If dependencies are added later, add a `composer.json` and run `composer install --no-dev --optimize-autoloader` in the Dockerfile.
