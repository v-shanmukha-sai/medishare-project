ABSTRACT

MediShare is a web-based medicine donation and distribution platform that connects verified medicine distributors and pharmacies with non-governmental organizations, medical shops, old-age homes, orphanages and charitable hospitals. A large quantity of usable medicine is wasted every year because distributors hold surplus or near-expiry stock while social organizations struggle to obtain medicines for the people they serve. MediShare addresses this gap with a single, verified marketplace.

The application provides role-based access for administrators, distributors and organizations. Distributors publish stock with batch number, expiry date, price and quantity. Organizations search the store, add medicines to a cart, choose a delivery address and pay through Razorpay (UPI, card or net banking) or cash on delivery. Every order passes through a controlled lifecycle: Pending Payment, Pending, Accepted, Packed, Shipped, Out for Delivery and Delivered. Stock is reserved when an order is placed and restored when it is cancelled or rejected. Expired and out-of-stock medicines are removed automatically and the distributor is notified.

The system is implemented with PHP 8 on Apache, PostgreSQL hosted on Supabase, Bootstrap 5 and vanilla JavaScript. It includes admin verification of documents, in-app notifications with an unread badge, reviews, reports with CSV export, audit logs, an email-OTP password-reset flow and performance optimizations for a hosted database. The platform was tested at the API and browser levels; all functional tests passed and cached read paths respond in milliseconds.

Executive Summary

MediShare is a complete web application for redistributing usable medicines from verified distributors to verified social organizations. It replaces informal phone and spreadsheet coordination with a single platform that shows live stock, expiry dates, prices and order status.

The platform has three roles. Distributors manage their medicine inventory. Organizations browse the store, place orders and pay online or choose cash on delivery. Administrators verify accounts, review uploaded documents and monitor reports and audit logs.

The main outcomes of the project are:

  • a verified network of distributors and recipient organizations;
  • expiry-aware inventory with automatic removal of expired and out-of-stock medicines;
  • an order lifecycle with stock reservation, cancellation, rejection and delivery tracking;
  • server-verified Razorpay payments with UPI, card and net-banking support, plus cash on delivery;
  • in-app notifications with an unread badge;
  • reviews, reports with CSV export and a complete audit trail;
  • an email-OTP password-reset flow;
  • caching and lazy database access that keep cached reads in the millisecond range.

The system was validated with API tests, browser tests and a role-based smoke test. All functional checks passed.

[[SEC:intro]]

1. Introduction

1.1 Background

Medicines are essential, time-sensitive products. Distributors and pharmacies routinely carry surplus stock, and a portion of it approaches expiry before it can be sold. At the same time, NGOs, old-age homes, orphanages, charitable hospitals and small medical shops often lack the funds and supply network to obtain even basic medicines. Much of the surplus is discarded while genuine demand remains unmet.

Most redistribution today happens through phone calls, messaging applications and personal contacts. These channels do not provide verified participants, live stock information, price transparency, order tracking, payment records or an audit trail. MediShare was built to replace this informal process with a structured digital platform.

1.2 Purpose of the Project

The purpose of the project is to design and implement a reliable, easy-to-use platform where verified distributors can list surplus or near-expiry medicines and verified organizations can order them. The project also demonstrates a complete software development cycle: requirements, design, implementation, testing and deployment.

1.3 Scope of the Report

This report describes the problem, the proposed solution, the system architecture, the database design, the implementation of each module, the security and performance measures, and the testing results. Setup instructions and an API reference are included in the appendix.

[[SEC:problem]]

2. Problem Statement & Motivation

There is no common, trustworthy platform where verified distributors can list surplus or near-expiry medicines and verified social organizations can order them. The absence of such a platform causes avoidable wastage of usable medicines, difficulty for organizations in finding suppliers, no verification of the parties involved, no record of donations, payments or deliveries, no visibility of expiry dates and stock levels, and manual, error-prone order handling.

The motivation for the project comes from three observations:

  • medicine waste is often a logistics and visibility problem rather than a shortage of demand;
  • social organizations need a simple ordering experience, not a complex enterprise system;
  • trust is essential, so every distributor and organization must be verified before participating.

MediShare addresses these issues with verified accounts, a live store, a controlled order lifecycle, online payments and an audit trail.

[[SEC:arch]]

4. System Architecture

MediShare uses a three-tier architecture. The browser renders static pages and JavaScript modules. The application tier is a set of PHP endpoints running on Apache. The data tier is a PostgreSQL database hosted on Supabase. External services provide payments and email OTP delivery.

        v

        |            --->  Supabase Auth (password-reset OTP)
        |
        |  PDO (prepared statements)
        v
PostgreSQL database (Supabase)

4.1 Modules

  • Authentication and verification: registration, login, logout, sessions, document review and account approval.
  • Medicine inventory: add, edit, remove, stock, expiry, batch, category, price and images.
  • Store and cart: search, filters, cart persistence, delivery address and geolocation.
  • Order management: order creation, grouping by distributor, status transitions, cancellation and rejection.
  • Payments: Razorpay order creation and signature verification, cash on delivery and payment status.
  • Notifications: in-app notifications, unread badge and periodic refresh.
  • Reviews: one review per delivered order with rating and comment.
  • Reports and audit: revenue and order statistics, CSV export and activity log.
  • Password reset: email OTP, reset token and password update.
  • Profile and map: profile updates, delivery location and a public map page.

4.2 Design Principles

  • Role-based access is enforced on the server, not only in the interface.
  • Every write that affects stock runs inside a database transaction.
  • Payment confirmation depends on a verified gateway signature.
  • Read-heavy responses are cached briefly and invalidated on writes.
  • Removed medicines are soft-deleted so historical orders remain intact.

6.1 Relationships

  • One user has at most one distributor profile or one organization profile.
  • One distributor owns many medicines.
  • One organization places many orders; one order belongs to one distributor.
  • One order contains many order items and has one transaction.
  • One delivered order can have one review.

6.2 Design Notes

Medicine rows use a soft-delete flag because order items reference them. Prices are copied into order items at the time of ordering so later price changes do not alter historical orders. Order totals are computed on the server. Status values are constrained so that only valid lifecycle states can be stored.

[[SEC:impl]]

7. Implementation

7.1 Authentication and Role Management

Registration collects the user's name, email, password, phone, address, city, coordinates, role and, for distributors and organizations, license or registration details and an uploaded document. Passwords are stored with password_hash() and verified with password_verify(). A successful login regenerates the session ID and stores the user's identity in the PHP session. Protected endpoints call a shared role check, and the dashboard hides tabs that are not allowed for the current role.

7.2 Admin Verification and Documents

New distributor and organization accounts remain unverified until an administrator approves them. The verification page lists pending accounts and shows a thumbnail of the uploaded document, which opens the full image in a new tab. Approve and reject actions are written to the audit log.

7.3 Medicine Inventory

Distributors add medicines with name, category, price, MRP, stock, batch number, expiry date, shelf life and image. Existing medicines can be edited. Removal uses a soft-delete flag so past orders and invoices remain intact. When stock reaches zero, the medicine is removed from the store and the distributor is notified. Expired medicines and out-of-stock medicines are also removed automatically when the store is loaded, and a low-stock notification is generated below the configured threshold.

7.4 Store, Cart and Geolocation

The store shows available medicines with distributor name, category, price, stock, expiry and shelf life. Users can search by name and filter by category, remaining shelf life and distributor. The cart is stored in the browser so it survives page reloads. Delivery location is captured through the browser geolocation API and stored in a cookie; if permission is denied, checkout proceeds with the delivery address alone.

7.5 Order Management

When an order is placed, the server validates each medicine, checks expiry and stock, deducts the ordered quantity, groups items by distributor and creates one order per distributor. The minimum order value is ₹500 per distributor. The order, its line items and its transaction are written inside a database transaction. Organizations can cancel an order while it is Pending or Pending Payment; the cancellation restores reserved stock and marks the transaction as Cancelled. Distributors can reject pending orders, which also restores stock.

7.6 Notifications, Reviews and Reports

Notifications are stored in the database with a type, text and read status. They are generated for new orders, payment confirmation, acceptance, rejection, cancellation, delivery, low stock and expiry. The navigation bar shows an unread-count badge refreshed every 60 seconds. Organizations can review a delivered order once, with a rating and an optional comment. Reports show revenue, order counts, medicine counts and stock distribution, with CSV export. The audit log records sensitive actions with the user and timestamp.

[[SEC:orders]]

8. Order Lifecycle & Payments

8.1 Status Flow

Razorpay:  Pending Payment --(verified payment)--> Pending
Cash:      Pending (immediately)

Pending --(distributor accepts)--> Accepted --> Packed --> Shipped
        --> Out for Delivery --> Delivered

Pending / Pending Payment --(organization cancels)--> Cancelled
Pending --(distributor rejects)--> Cancelled

Stock is deducted when the order is created. If an order is cancelled or rejected, the stock is restored. When the last units of a medicine are ordered, the medicine is marked removed and the distributor is notified. An unpaid Razorpay order cannot be accepted by the distributor, so payment confirmation is enforced on the server.

8.2 Online Payments

The server creates a Razorpay order with the server-computed total, stores the gateway order reference in the transaction row and returns the public key and order details to the browser. The Razorpay checkout supports UPI, cards and net banking, and UPI can be pre-selected so that the UPI section opens first.

After payment, the browser sends the Razorpay order ID, payment ID and signature to the server. The server recomputes the HMAC-SHA256 signature with the secret key and compares it using a timing-safe comparison. Only a valid signature moves the orders from Pending Payment to Pending and marks the transaction as Completed.

8.3 Cash on Delivery

Cash orders are confirmed immediately with a Pending transaction. The distributor can mark the payment as received after delivery. Payment status is displayed separately from order status so that the two concerns are not confused.

[[SEC:security]]

9. Security

Security was treated as a cross-cutting concern rather than an add-on. The main measures are:

  • passwords hashed with password_hash() and verified with password_verify();
  • prepared statements for every database query to prevent SQL injection;
  • role checks on every protected endpoint, not only in the interface;
  • session ID regeneration after login;
  • HMAC-SHA256 verification of Razorpay payments with a timing-safe comparison;
  • HMAC-signed, expiring password-reset tokens;
  • generic responses for unknown email addresses to prevent account enumeration;
  • a five-attempt limit on OTP verification;
  • .htaccess denies for the configuration and log folders;
  • PHP execution blocked inside the uploads folder;
  • credentials stored in config/secrets.php, which is excluded from Git;
  • user-uploaded license documents and logs excluded from Git;
  • audit logging of sensitive actions.

The password-reset flow sends a 6-digit OTP through Supabase Auth, verifies it on the server, and issues a short-lived reset token. The new password is hashed before storage.

[[SEC:perf]]

10. Performance Optimization

Because the database is hosted remotely, a cold database round trip costs hundreds of milliseconds to several seconds. The following optimizations were applied:

  • Short-lived file cache: read-heavy GET endpoints cache JSON responses for 10–20 seconds. Every POST clears the cache, so writes are visible immediately.
  • Lazy database connection: endpoints check the cache before opening a database connection, so cache hits avoid the database entirely.
  • Session lock release: the PHP session is closed after reading the current user, allowing parallel requests.
  • Combined queries: report statistics were reduced from four queries to one.
  • Prefetching: the dashboard warms the APIs for all tabs after login, so tab switches hit the client or server cache.
  • Client-side cache: the dashboard keeps GET responses for 30 seconds and the store keeps them longer.
EndpointCold responseCached response
Orders~916 ms5–32 ms
Medicines~1403 ms3–4 ms

The results show that caching and lazy connections remove most repeated database latency while short TTLs and write invalidation keep data fresh.

[[SEC:future]]

12. Limitations & Future Work

12.1 Limitations

  • Email and SMS delivery require external configuration; email is disabled by default and SMS is a stub.
  • Razorpay is used in test mode; live payments require live keys and compliance checks.
  • There is no integration with courier or delivery-partner APIs.
  • Geolocation depends on browser permission and may be inaccurate.
  • The application is a responsive web app, not a native mobile app.
  • The hosted database adds network latency to cold requests.
  • Admin verification is manual, and the interface is available in English only.

12.2 Future Work

  • Enable live Razorpay payments and configure SMTP for real email delivery.
  • Integrate an SMS gateway such as Twilio or MSG91.
  • Add delivery-partner tracking and route optimization.
  • Add barcode or QR scanning for medicine batches.
  • Use OCR to assist license verification.
  • Add demand forecasting and early expiry alerts.
  • Build a mobile application for distributors and field staff.
  • Add multi-language support, accessibility improvements, backups and monitoring.
[[SEC:conclusion]]

13. Conclusion & References

13.1 Conclusion

MediShare demonstrates how a focused web application can reduce medicine wastage and improve access for social organizations. The project covers the complete operational cycle: registration, verification, inventory, store, cart, payment, order tracking, cancellation, notifications, reviews, reports and password recovery.

The implementation emphasizes correctness at trust boundaries: verified accounts, server-side payment verification, transactional stock handling, role-based authorization and audit logging. Caching and lazy database access keep the interface responsive despite a hosted database. The system is ready for extension with live payment credentials, real email and SMS delivery, and delivery-partner integration.

A. Setup Instructions

  1. Install XAMPP with PHP 8.2 and enable the pdo_pgsql and curl extensions.
  2. Import database.sql into a PostgreSQL or Supabase database.
  3. Copy config/secrets.example.php to config/secrets.php and fill in the database, Razorpay and Supabase values.
  4. Place the project under the Apache document root and open index.html.
  5. For password-reset email, add {{ .Token }} to the Magic Link template in Supabase Authentication → Email Templates.
